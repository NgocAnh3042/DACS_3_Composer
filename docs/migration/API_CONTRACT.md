# FoodHub PHP API contract để chuyển sang Spring Boot

> Tài liệu được lập bằng cách đọc mã trong `backenddd/` và Android API client tại thời điểm hiện tại. Đây là hợp đồng quan sát được từ implementation, không phải cam kết PRD. Không kết nối dịch vụ/DB khi lập tài liệu. Không đưa secret vào đây. Mọi endpoint nối tiếp base path `/api/`; PHP router lấy Firebase Bearer token trước khi dispatch, ngoại trừ health check, preflight và PayOS webhook.

## 1. Quy ước chung

### 1.1 Response và kiểu dữ liệu

- Thành công thường là `{"data": [...]}`, `{"data": {...}}`, `{"id":"..."}`, `{"ok":true}`. Ngoại lệ được ghi riêng bên dưới. Lỗi thường `{"error":"..."}`. Các AI/recommendation route có thể trả `success` ngoài `data`.
- Khóa DB BIGINT mà API đưa ra thường serialize thành **string** (kể cả user/store/order/message/conversation/dish/address ID). Các giá, số đếm, tọa độ trả dưới dạng JSON number; cờ là boolean; trường tùy chọn có thể là `null` hoặc chuỗi rỗng theo endpoint. Xem mapper cụ thể.
- Database enum/status thường chữ thường; API thường uppercase một số response như role/status/payment/message type. Request status được lowercase trước khi lưu. Các alias được nêu ở endpoint tương ứng.
- JSON body đọc bằng `body()`; JSON sai trả HTTP 400 `{"error":"JSON không hợp lệ"}`. Các nhánh throw/validate thường trả 4xx; catch tổng router trả HTTP 500 `{"error":"Lỗi xử lý yêu cầu"}`. Một số AI/provider/config lỗi trả 503 với thông báo an toàn.
- Header CORS hiện tại: `Access-Control-Allow-Origin: *`; headers cho phép `Authorization, Content-Type`; methods `GET, POST, PUT, PATCH, DELETE, OPTIONS`. OPTIONS trả 204 không body.
- Gzip được bật qua `ob_gzhandler` nếu PHP zlib có và client yêu cầu gzip. GET `categories`, `stores`, `dishes` có `Cache-Control: private, max-age=60, stale-while-revalidate=120`, ETag SHA-256 nội dung và trả 304 khi `If-None-Match` khớp.
- Route logger ghi method, route đã khử ID thành `{id}`, thời gian ms và tổng câu execute SQL. Không ghi query/body/token. Dòng nguồn: `backenddd/api/index.php:8-9,14-37,210-226`; PDO query counter: `backenddd/database/connection.php:4-39`.

### 1.2 Firebase token, user và role

- Bearer lấy từ `Authorization: Bearer ...`. ID token phải có `alg=RS256`, `kid`, chữ ký hợp lệ từ Firebase X.509; kiểm `aud` trùng project, `iss=https://securetoken.google.com/{project}`, `sub` không rỗng, `exp` còn hạn, `iat` không quá 60 giây tương lai. Public cert cache file ngoài public directory, TTL theo Cache-Control/Expires/Age; thiếu kid thì refresh một lần. Nguồn: `backenddd/api/index.php:42-151,198-206`.
- Mỗi nghiệp vụ thông thường gọi `account()` để map `claims.sub` tới `users.firebase_uid`; hồ sơ thiếu trả 404 yêu cầu `POST /users/me`. Nguồn: `backenddd/api/index.php:157-175,261-263`.
- `GET /` là ngoại lệ không yêu cầu token nhưng vẫn cần DB để báo health. `OPTIONS` là preflight. `POST /payos/webhook` bỏ Firebase Bearer và xác thực HMAC PayOS riêng.
- `POST|PUT|PATCH /users/me`: tìm hồ sơ theo UID; nếu UID mới nhưng claim email đã xác minh, tìm row cùng email còn hoạt động rồi cập nhật Firebase UID để giữ khóa số và dữ liệu. Nếu chưa có row, tạo user thường; không cho tự cấp admin. Nếu đã có row, cập nhật tên/email/phone/address/avatar/last_login. Nguồn: `backenddd/api/index.php:329-359`.
- Role DB → Android: `customer → user`, `seller → restaurant`, `driver → shipper`, `admin → admin`. Nhánh đăng ký nhận `restaurant/seller/nhà hàng → seller`, `shipper/driver → driver`, còn lại customer. Nguồn: `backenddd/api/index.php:161-175,349-358`.

### 1.3 Tính tiền đơn chuẩn

- Server lấy giá món còn bán hiện tại từ DB, không tin giá client; mỗi dòng nhân số lượng (clamp 1–99), cộng subtotal. Phí giao mặc định lấy cấu hình `delivery_fee` (mặc định 15000); tới 3km phí gốc, trên 3km thêm 10000 cho mỗi km lẻ làm tròn lên. Không có tọa độ hợp lệ thì vẫn tính phí gốc. Nguồn: `backenddd/api/index.php:55-76,550-563`.
- Voucher kiểm tra active, ngày hiệu lực, phạm vi quán, min order, usage limit. `percentage`: subtotal × phần trăm, giới hạn `max_discount` nếu có; `fixed`: giá trị cố định; `free_shipping`: bằng phí giao. Giảm không vượt subtotal + phí giao. `total=max(0,subtotal+fee-discount)`. Nguồn: `backenddd/api/index.php:563-565`.

### 1.4 PayOS webhook

- Bỏ `signature`, sort keys trong `data` theo thứ tự chuỗi; chuẩn hóa null/`"null"`/`"undefined"` thành rỗng, boolean thành `true|false`, array thành JSON; ghép `key=value` bằng `&`; tính HMAC-SHA256 với checksum key cấu hình, so sánh constant-time `hash_equals`. Tiếp đó xác minh payment link và số tiền bằng cả `payments.amount` lẫn `orders.total_amount`; transaction ghi event id/hash, cập nhật payment/order/log, commit, rồi ghi notification và gửi FCM nếu trạng thái mới chuyển paid. Nguồn: `backenddd/api/index.php:240-259`.

### 1.5 Tên cấu hình cần port (chỉ tên)

- Firebase: `firebase_project_id`, `firebase_service_account_file`.
- MySQL/TiDB: `mysql.host`, `mysql.port`, `mysql.database`, `mysql.username`, `mysql.password`, `mysql.charset`, `mysql.timezone`, `mysql.ssl.required`, `mysql.ssl.ca`.
- Nghiệp vụ: `delivery_fee`; PayOS: `payos.client_id`, `payos.api_key`, `payos.checksum_key`; AI providers: tên biến/cấu hình được đọc trong `backenddd/ai/MealAdvisor.php` và `backenddd/config.gemini.example.php` (không chép giá trị); cache: `cache_directory`.
- PHP nạp cấu hình theo `config.local.php`, `config.runtime.local.php`, `config.example.php` ở `backenddd/api/index.php:228-234`. Không chuyển file local/credential vào Git hay webroot.

## 2. Endpoint nghiệp vụ trong `backenddd/api/index.php`

Các lỗi chung ngoài lỗi được nêu riêng: 400 JSON không hợp lệ/sai ID, 401 thiếu hoặc token sai, 403 sai role/quyền, 404 không có row/route, 409 xung đột trạng thái, 422 dữ liệu nghiệp vụ không hợp lệ, 503 DB/cấu hình/cert không sẵn sàng, 500 lỗi không xử lý được. Response thành công và field giữ nguyên là ưu tiên số một khi viết Spring.

## 4. Error contract theo nhóm

| HTTP | JSON shape | Trigger tiêu biểu |
|---|---|---|
| 400 | `{"error":string}` | JSON body parse fail; ID định dạng sai |
| 401 | `{"error":string}` | Missing Bearer, Firebase signature/claim/kid invalid |
| 403 | `{"error":string}` | Role, ownership, conversation membership, inactive AI account |
| 404 | `{"error":string}` | Resource missing, profile/store/dish/order not found |
| 405 | `{"error":string}` | Unsupported verb in AI/recommendation subroute |
| 409 | `{"error":string}` and some AI/order-draft conflicts also `data` | Driver/order conflict, draft conflict, payment already settled |
| 422 | `{"error":string}`; some AI draft errors include `data` | Validation, quote/schedule/voucher/request fields |
| 500 | `{"error":"Lỗi xử lý yêu cầu"}` | Generic router failure; webhook has its own generic message |
| 502 | `{"error":string}` | PayOS create-link upstream response invalid |
| 503 | `{"error":string}` | DB/Firebase cert/provider/config unavailable |

## 5. Android actually-used routes

The app uses a generic `FoodHubApi` with `{resource}` routes, so inspect call arguments as well as Retrofit annotations. Typed `AuthApi`, `OrderApi`, `RestaurantApi`, `SearchHistoryApi` declare overlapping routes; they do not imply all call sites use the typed interface.

### Observed call-site coverage

- Authentication/profile: `GET /users/me`, `POST /users` and `POST /users/me`; profile/admin user reads and updates use `/users`, `/users/{uid}`.
- Catalog: `GET /stores` (home/customer lists pass through `StaleListRepository`), `/stores/{id}`, `/stores/mine`, `/dishes` (including restaurant/category filters and restaurant management `includeUnavailable=1`), `/categories`; dish create/update/delete.
- Orders: GET `/orders`, `/orders/{id}`, `/orders/available`; POST `/orders`; PATCH `/orders/{id}`; POST `/deliveries/{orderId}/accept`.
- Users/addresses: `/users`, `/users/me`, `/users/{uid}`, `/addresses`, `/addresses/{id}` CRUD paths via generic API. The admin customer screen also calls `POST /users/me` with an admin-entered profile payload; the endpoint's actual authorization/role rules still apply.
- Chat: GET/POST `/conversations`, GET/POST `/conversations/{id}/messages` (the same GET passes `limit`); read action uses POST message endpoint.
- Payments: GET `/payments`, POST `/payments/create-link`; checkout gateway return goes through Android deep link. The old `PaymentApiService.kt` contains `/api/payment/...` paths that do not match the current PHP routes and should not be treated as active PHP integration unless a caller is found.
- Device tokens: POST `/device-tokens` via `FirebasePushService`.
- Activity: POST `/activity_logs` via `ActivityLogRepository`.
- Recommendation: GET `/recommendations/personalized`, GET/POST/DELETE `/search/history`, GET/PATCH `/recommendations/preferences`.
- AI meal advisor: POST `/ai/meal-advisor`; AI draft route usage should be checked callsite-by-callsite if enabled in UI.
- Admin promotions: GET/POST/PATCH/DELETE `/promotions` and `/promotions/{id}`.
- Notifications: GET `/notifications`, PATCH `/notifications/read-all`.

Key Android transport files: `app/src/main/java/com/example/dacs_3_composer/data/remote/FoodHubApi.kt` (generic verbs and cached token), `ApiServices.kt` (typed declarations). Call-site examples: `MainActivity.kt:89-99`, `feature/auth/presentation/AuthViewModel.kt:61-71`, `data/repository/ChatRepository.kt`, `PaymentRepository.kt`, `RecommendationRepository.kt`, `MealAdvisorRepository.kt`, `FirebasePushService.kt`, `ActivityLogRepository.kt`.

### Server endpoint inventory not confirmed as Android-used

At current static callsite search, these PHP endpoints have no confirmed direct Android caller: `POST /payments` (legacy write), `GET /ai/preferences`, `PUT /ai/preferences`, `PUT /ai/preferences/consent`, `DELETE /ai/preferences`, `DELETE /ai/preferences/{field}`, `POST /ai/feedback`, `GET /ai/metrics`, AI order-draft endpoints under `/ai/order-drafts` (check UI feature before removal), plus `POST /payos/webhook` is not an Android endpoint at all (gateway calls it). Some declared APIs may be unused through typed clients; direct callers for `/notifications/{id}` (single-read) and most profile CRUD admin variants were not found, while `/notifications/read-all` is used. `GET /` and `OPTIONS` are infrastructure calls, not app features. **Do not delete based only on this list**: search every Android source and server-to-server callback before removing.

## 6. Spring Boot migration checklist

1. Freeze JSON names and types above with contract tests; pay particular attention to aliases, uppercase status/role, string IDs, null vs empty, direct PayOS checkout response, recommendation top-level shape, and AI error bodies.
2. Implement cross-cutting Firebase verification + account lookup before business controllers; maintain mapping `firebase_uid` ↔ numeric `users.id`.
3. Port ordinary CRUD groups first (stores/dishes/categories/addresses), then user, orders/delivery, payment/webhook, chat/FCM, finally AI/recommendation. Do not move PayOS or AI provider keys to Android.
4. Use explicit DTOs instead of serializing DB entities. Preserve transaction boundaries and post-commit notification behavior.
5. Confirm Android Retrofit paths against the contract. `PaymentApiService.kt` has legacy path candidates that require separate verification.
